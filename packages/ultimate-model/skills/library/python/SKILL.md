# Python 开发规则

> 来源：Qoder rules/python.md（2026-10-13 移植）。

## 一、类型（公共接口不是"隐性契约"）

- **必须标注**：公共函数、脚本入口、跨模块数据结构。
- **`Any` 出现要写理由**（等于关掉这块检查）；能收窄就收窄，别拿 `Any` 图省事。
- 结构用 **`dataclass` / `TypedDict`** 描述，**不用裸 `dict` 传字段**。
- 真要做类型检查就配 mypy / pyright 并**按严格档起步**——别一边写一边放宽。
  判据：`mypy --strict <pkg>`（或项目既有配置）退出码 0；新增 `Any` 在同一提交里带注释说明。

## 二、结构与设计

| 判据 | 怎么做 |
|---|---|
| 纯逻辑与 IO 分离 | IO 留在边界（文件 / 网络 / 环境变量），逻辑部分能脱离 IO 单测 |
| 一个模块一件事 | 避免全局可变状态；组合优于继承 |
| 设计模式 | **只在解决已出现的重复时**引入，不预置 |
| 类方法 >10 个、文件 >300 行 | **先想拆**；拆不动要写出为什么 |

## 三、错误处理

- **禁止吞异常**：`except Exception: pass` 一律不接受；真要忽略必须**写清原因并记录**。
- 自定义异常继承项目基类并**带上下文**（哪个输入 / 哪个外部调用失败）。
- **只在系统边界校验**（用户输入 / 外部 API / 文件 / 环境变量）；内部信任契约，不层层重复校验。
- **批量处理先定策略**：遇错即停 vs 继续并汇总失败清单——**默认后者，且失败明细落盘**；否则"跑完了"看不出漏了哪几条。

## 四、测试

- **pytest + fixture 管资源**（`tmp_path` / `monkeypatch`），不自己造 setUp/tearDown 样板。
- **外部依赖在边界处替换**，不 mock 自己写的纯函数。
- 断言要能失败：别拿"函数被调用过"当结论（只写 `assert_called_once` 不算）；**断言行为结果**，关键路径配**负对照**。
- 覆盖与选型细则见技能 `assertion-discipline`。

## 五、性能

- **先测量再优化**：`cProfile` / `timeit` 拿基线 → 改 → **再测一次对比**；没基线不许说"优化了"。
- 热点优先改**算法与批量 IO**，不先抠语法细节。
- **大文件流式处理**，不要 `readlines()` 全量进内存；判据：峰值内存不随文件大小线性增长。

## 六、验证（脚本类交付）

- **真跑一次 + 断言输出**：退出码、关键字段、行数——别只看"没报错"。
  反例：脚本把异常打印出来但退出码 0，被当成"跑通了"。
- **依赖安装走官方源**（镜像可能误报"无可用版本"）；**装完 `import` 复验**，不靠"pip 说装好了"。
