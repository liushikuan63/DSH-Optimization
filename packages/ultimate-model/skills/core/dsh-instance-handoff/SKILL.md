# DSH 实例维护与交接

先确定实际阻塞是当前进程持有的文件、启动时才加载的配置，还是与实例无关的错误。能在当前授权内通过后台接口完成就继续，不为普通文件变更强行交接。

1. 从当前进程与启动环境确认 exe、PID/父进程、`DSH_HOME`、profile 和版本；历史路径、目录名和已安装文件不证明实际实例归属。确认目标有没有活跃任务，未知不能当作空闲。
2. 需要关闭或重启时，先给具体影响、备份、恢复方式并核对已有授权。已有当前实例和动作的明确授权可以执行；缺少这项授权则先完成可做部分，不能通过另一实例、提权或 helper 绕开。
3. 将交接放到双方确实可读的任务专用 `<HANDOFF_ROOT>`，由任务指定真实位置。结构可用 `inbox/<task-id>.md`、`outbox/<task-id>.result.md` 与 `done/`；不假定两套 home 互相可见。
4. 任务书包含目标、授权范围、实例归属、脏文件与备份、准确命令、退出码判据、回退、已验/未验和下一步。不携带账号、密钥或完整聊天。执行方仅做授权范围，遇到冲突保存原始失败与回执。
5. 经授权需要独立维护进程时，以隐藏窗口启动任务拥有的 helper，保存 PID 和日志，校验退出与恢复。示例：`Start-Process pwsh -ArgumentList '-NoProfile','-File','<已审查脚本>' -WindowStyle Hidden`。脚本不是本包附带资产，必须先存在、审查且绑定准确实例。
6. 发起方读回执行结果并独立复核：新 PID/版本、正确 home/profile、实际配置读取、关键工具或 UI 路径、原会话和用户数据保留。回执已写、命令派发成功、端口响应或新进程存在都不足以独自证明恢复完成。

不同版本的 `dsh plugin`、headless profile 和环境继承行为可能变化。安装前只读核对 diagnostics 的实际目标目录与权限；不将设置 DSH_HOME、符号链接或某个旧版默认值当作隔离/授权证明。应用管理的依赖与动态运行时路径保持其约定，不为解析失败盲目复用另一 profile 的 node_modules。

电脑操作先用现有文件、CLI、应用 API/HTTP/CDP 或后台控件，随后按当前用户选择使用后台 CUA、支持前台的入口或内置 Computer Use。切换到会占前台的入口前简短说明，绑定新鲜窗口状态并读回结果；只支持后台的适配器拒绝时不能强塞前台参数。工具切换沿原目标和动作授权，不扩大敏感访问或外部发送。
