# git 交付纪律（提交 / PR / 发布 / 部署）

**与 `ship-clean-svn` 的分工**：先确认目标仓是 git 还是 SVN——是 SVN 就走 `ship-clean-svn`；
本技能用于 **git 仓**（上游 / 开源 / fork）。两者的"只加明确路径 + 先分辨归属"是同一条纪律。

来源：Qoder 侧 `rules/delivery-pr.md`，2026-09-20 迁移为 DSH 技能。

## 一、提交 / 部署前的硬门槛（最高优先级；**按影响面分档**）

**门槛强度看动作影响面**——本地提交是可回退的本地动作，对外可见动作才是全绿门槛：

- **本地增量提交**：一条属于本轮、能失败的判据 + 本轮编译退出码 + 受影响路径手工走通，就够提交。
- **推送 / 部署 / 发版**：**完整检验不通过，不得推送、不得部署**——
  - 测试全绿（批量模块**一次跑全**，中途中断等于没验证）
  - 服务类改动**真启动** + 关键路径走通
  - 前端改动**真实浏览器**验证（见 `verify-ui-in-browser`）
- 任何一项没验证，就**明确写"未验证"**，而不是跳过不提

## 二、提交前：分辨改动归属

跑 `git status`，区分**「本轮改的」**与**「工作区里本就有的」**。同一仓库可能有多会话 / 多 AI 并行改动：

- 非本会话的改动：**不提交、不还原、不修改**——汇报里单列一节即可，**不影响本批次收尾**（不为它停下等确认）。
- 需要还原探针/临时改动时：**先备份再还原**，不要用 `checkout` 抹掉别人的编辑。

## 三、只加明确路径

- `git add <具体文件>`；**禁止** `git add -A` / `git add .`（守卫会硬拦）。
- 暂存后**复核一遍**没混入敏感文件（`.env`、凭据、证书）与构建产物。
- 提交前看一遍 `git diff --cached`，确认的就是将要提交的内容。

## 四、说明语言跟随仓库

- 上游 / 开源仓库用**英文**（讲清 why / impact / verification）。
- 内网仓库沿用**团队既有语言**。
- 面向用户的回复仍用中文（与仓库语言无关）。

## 五、推送前同步上游

**让目标分支与上游一致，PR diff 只含本批次文件**——否则会混进几百个同步文件，评审无法进行。
判据：`git diff upstream/main...HEAD --name-only` 的文件数与你本批次的改动文件数一致。

## 六、唯一 PR

fork / 上游里**未合入主分支的旧 PR 要撤回，只保留当前一条**。
**撤回 / 关闭是对外可见动作，先给选项让用户拍板**，不要自行操作。

## 七、汇报格式（固定）

```
PR：<链接>
范围：<文件数> 个文件，+<增> / -<删> 行
状态：mergeable / 冲突
验证：<本轮实际跑的命令 + 退出码 + 覆盖范围>
未验证 / 未做：<逐条写清，不得与已落地混写>
```

## 八、反模式速查

| 反模式 | 正例 |
|---|---|
| `git add -A` 一把梭 | `git add src/a.ts src/b.ts`，再 `git diff --cached` 复核 |
| "改完了，我提一下" | 先跑该影响面对应的判据（本地提交 = 一条能失败的判据 + 编译退出码；推送 / 部署 = 完整检验），通过后再提交；未通过就写"未验证，未提交" |
| PR 里混进上游同步的几百个文件 | 推送前 rebase/merge 上游，确认 diff 只含本批次 |
| 旧 PR 挂着不管 | 撤回旧 PR（**先让用户拍板**），只留当前一条 |
| 用 `checkout` 还原别人的改动 | 先 `git status` 分辨归属，只还原本会话产物，且先备份 |

## 九、重要交付加一道独立对抗审查

- **触发范围（仅这几类）**：鉴权 / 数据 / 计费 / 迁移，或跨模块 / 接口级大改动。**小步修补不加这一道**，只需完整检验（见 §一）。
- **做法**：推送前把**最终 diff** 交给**全新上下文的只读子代理**——**只给 diff、先不给自己的结论**，专门挑功能缺陷与反例（已装 `ocr` CLI 时可用 `open-code-review-delegate` 技能）。
- **判据要能失败**：子代理结论必须落到「哪一行 + 什么反例」；**回报为空不等于通过**——要能说出它看过哪些改动、哪些放过了。
