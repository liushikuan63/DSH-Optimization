# 写测试与断言的纪律

**与 `verify-before-claim` 的分工**：那个技能回答"**结论需要什么强度的证据**"（测试、真启动、真请求、截图分层）；
本技能回答"**有测试框架时**怎么写断言"。两者不重叠，可同时加载。

来源：Qoder 侧 `rules/testing.md`，2026-09-20 迁移为 DSH 技能。

## 一、断言必须能失败（首要判据）

写完每条断言先问一句：**"它失败得了吗？"** 被改坏时会红的断言才算数。

| 反模式 | 为什么等于没写 | 正例 |
|---|---|---|
| `if (ok) { … } else { 断言失败 }` | 两边都算过，改写逻辑时它永远绿 | 直接断言期望值本身：`assert(result === expected)` |
| 只断言"没抛异常" | 空实现也满足 | 断言具体返回值 / 副作用 / 调用次数 |
| 断言恒真表达式（`assert(true)`、`assert(x == x)`） | 恒绿 | 断言被测函数产出 |
| 断言比被测逻辑还复杂 | 错在测试里看不出来 | 期望值写死为字面量 |

**自检动作**：把被测代码临时改坏一处，确认对应用例**变红**；仍绿说明这条断言是假绿。

## 二、计数型断言（最容易假绿的一类）

"某集合应有 N 项"这类断言：

1. **先把该断言行之前所有会增删对象的操作列一遍**，再定这个 N——数字要能一句话说清怎么来的。
2. 确认**摘掉被测的过滤条件后它仍会变红**（否则 N 恰好等于全集时，过滤失效也看不出来）。
3. 聚合类断言避免只写"大于 0"；要写清期望的具体条数或范围。

## 三、覆盖与修复绑定

- **异常路径与边界值必须有用例**，不能只有 happy path。
- **每条修复单独附带一个能复现原缺陷的测试**——先写红、再改绿，否则无法证明修的是这个缺陷。**无测试仓的降级路径**：改前先跑一次拿到能复现的坏读数，改后再跑拿正常读数，**两次读数**都写进汇报。
- 探针 / 检查器 / 守卫类代码：**先植入一次违规，确认它报红**，再撤掉；并给命中数加**下限断言**（0 命中是故障信号，不是"通过"）。

## 四、时间与外部依赖

- **时间边界夹具留足余量（≥100ms）**：不要让执行耗时自己跨过边界，否则会出现随机器负载抖动的偶发红。
- **外部依赖默认不参与断言**（网络、时钟、并发）：能注入替身就注入，否则把断言收敛到可确定的量；**不为等外部条件挂起用例**。

## 五、运行与汇报

- 批量模块的测试**一次跑全**；中途中断（某个模块挂了导致后面没跑）**等于没验证**。
- 报"全绿"时必须能说明三件事：**本轮编译退出码**、**测试命令**、**覆盖范围**。
- 未验证与已通过严格分开写（同 `verify-before-claim` 的两栏法）。

## 六、反模式速查

| 反模式 | 正例 |
|---|---|
| "测试全绿，应该没问题" | "`mvn test` 退出码 0，覆盖 X/Y/Z 三个模块共 42 个用例；A 模块未覆盖（无现存测试）" |
| 断言 `list.size() > 0` | 断言 `list.size() === 3`，并说明为何是 3（过滤后剩几条） |
| 修复缺陷只提交实现 | 同一提交里带一个先红后绿的复现用例 |
| 探针报"0 个问题"就当通过 | 先植入一个违规确认探针会红；并断言命中数 ≥1 |

## 七、测试分层与选型（要出测试计划时）

- **配比按测试金字塔**：单元多而快 → 集成适量 → E2E 少而高置信。层数不是目的，**每层失败能定位到哪**才是。
- **按组件类型选种类**：API 端点（业务单测 + HTTP 集成 + 消费方契约）、数据管道（输入校验 / 转换正确性 / 幂等）、前端（组件 / 交互 / 视觉回归 / 无障碍）、基础设施（冒烟 / 负载）。
- **覆盖优先级**（自上而下）：业务关键路径 → 错误处理 → 边界值 → 安全边界 → 数据完整性。**跳过** trivial getter/setter 与框架代码。
- 需要测试计划时产出四件并**指出既有覆盖缺口**：测什么 / 每块用什么类型 / 覆盖目标 / 示例用例。
  判据：示例用例里至少一条是**异常路径**；缺口必须点名文件或模块，不写"覆盖不足"这类不可核对的话。
