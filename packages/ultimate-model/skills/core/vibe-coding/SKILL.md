# 中大任务的推进流程（五阶段门禁 + 目标化执行）

> 来源：Qoder rules/vibe-coding.md + rules/long-task.md「大需求按五阶段推进」+ 参考包 skills/vibe-coding-workflow、vibecoding-doc、goal-driven-execution（2026-10-13 移植）。

大需求最容易死在两件事上：**在需求没说清时选技术栈**，和**一口气写完再调**。五阶段就是给这两件事上锁的。

## 一、五阶段推进（按影响分段检验；已有授权且准入满足时继续）

| # | 阶段 | 准入 | 产出 |
|---|---|---|---|
| ① | 需求澄清 | 用户描述过想做什么 | 谁用 / 什么场景 / 痛点 / 一次典型流程 + **≥3 个异常场景** + **可测试验收标准** |
| ② | 架构 | 需求与授权已清晰 | 到**文件级**的目录结构 + 每文件职责 + 数据流 + 模块接口约定 + **最脆弱 / 最不确定的一处** |
| ③ | 逐模块生成 | 架构已定 | 每模块：路径 / 职责 / 依赖与对外接口 + 最小验证（至少"能 import + 关键函数能调"） |
| ④ | 调试 | 有具体现象可复现 | 四步法记录 + 三行总结 |
| ⑤ | 迭代 | 有明确变更诉求 | 按切入点回到对应阶段 |

- **① 先不碰技术栈**：只谈谁用 / 什么场景 / 痛点 / 典型流程。用户已指定的技术栈直接保留；尚未清楚的业务不要用技术细节补造。验收标准要能失败：写"非法输入返回 400 且 `error.code=INVALID_PARAM`"，不写"输入校验完善"。
- **② 必须点名最脆弱的一处**："订单状态机的并发迁移没有现成方案，先按单机锁实现，多实例部署时会失效"——这句话是下一阶段排期与验收的依据。对已有充分需求和授权的增量任务，可在最小设计核对后持续实施，不另设设计签字。
- **③ 每模块保持清楚的输入输出和写域**；相关修改配能暴露缺陷的最小验证。依赖门失败先修复，独立且不受阻的模块仍可并行推进；共享写入和最终集成串行。
- **④ 调试四步**：完整报错 + 触发操作 + 期望/实际（三样缺一不可，"不行"不是报错信息）→ 解释原因（1–3 个可能 + 排查顺序，别直接改）→ 分步修（一步一验证，不一次改五处）→ 三行总结。
- **⑤ 迭代切入点**：加新功能 → 回 ①（这是新需求，不是补丁）；性能 / 体验 → 从 ④ 切入（有现象就有得查）；结构混乱 → 从 ② 切入（架构已撑不住当前需求）。判断不准时先从检索结果确认本技能的绝对目录，再用路由脚本：`node "<实际技能目录>/scripts/route-phase.js" "<现象>"`。
- **小任务不套用**：改一行文案、单点修复走常规流程。

## 二、长/复杂任务：维护 VibeCoding 文档并持续推进

1. **长/复杂任务默认沿现有 VibeCoding 文档/批次卡推进**；没有入口时在项目习惯位置创建最小文档，记录目标、授权、现状、依赖、分段验收、证据、写域、下一步和阻塞。避免同一任务另起平行台账。需求与授权已清晰（谁用 / 场景 / 验收说得出）就在首轮复述理解并推进；已明确授权不重复确认，不再问“要不要写文档”。
2. **仅对尚未裁定且影响目标、风险或验收的歧义提问**：先查可发现事实；只有确需用户选择时才给合理选项与推荐理由。若用户只授权出文档，实施仍是新授权范围；已授权实施则不因成文再加一次确认；本轮已明确要求长/复杂任务成文时直接完成，不问“要不要”。

使用当前可用的 `ask_user_question` 契约，不强制推荐标签或臆造超时参数。推荐、超时、自动返回不构成真人确认；等待期间只推进不依赖该裁决的已授权部分。正式 Plan/AgentTeams 和危险操作继续遵守各自批准门禁；澄清不提供操作授权。用户明确选“直接开工”且范围已获授权时继续，不重提同题。

| 选项 | 何时推荐 |
|---|---|
| 出单篇六节 | 小需求 / 单一功能 / 一屏能说清 |
| 出多文件包 | 完整项目 / 长任务 / 要分批交给 AI / 会跨会话 |
| 直接开工 | 需求其实已明确，或用户已表达过不想写文档 |

**判据**：只有需求还是感觉词时，首轮回复里才看得到提问（问的是文档粒度）；需求已清晰则看不到——复杂但清晰的任务里冒出"要不要写文档"式提问就是噪声（同 §四「不弹窗问"要不要"」）。

## 三、两种文档形态（不要另造第二套格式）

**六节是最小骨架**：技术规格类需求在这六个标题**内**自由扩写（加小节 / 加表格都行），仍然**不另造第二套格式**。

- **单篇 `Vibecoding.md`（小需求，标题 + 六节顺序固定）**：① Vibe 核心氛围（2–3 句，**多着墨**）② Intent 一句话意图 ③ User Stories 2–3 个具体场景 ④ Tech Stack Vibe（无偏好写"AI 自选最合适的现代技术栈" + 代码风格）⑤ Constraints 约束边界（明确的"不要做"）⑥ Success Vibe 成功标准（**多着墨**）。小需求若写着发现其实是完整项目，**当场升级为多文件包**，已写的六节留作 `B00` 的氛围锚。
- **多文件包（完整项目 / 长任务）**：`B00-共享上下文`（宪法 + 氛围锚，**每开新对话必发**：角色与目标 / 技术栈版本口径 / **铁律** / 目录约定与产物边界 / 固定流程）→ `总发起指令`（批次状态与装配对照表 + 可整段复制的总发起提示词 + 收尾自检 + **必须停下问的条件**）→ `B0x-批次卡`（按依赖排序，编号连续、依赖显式）→ `验收矩阵与台账`（每批一行：做了什么 / 怎么验的 / 没做什么）。
- **批次卡固定结构**：头部（依赖 / 工期 / 一句话风险）→ 开工提示词（4 反引号包裹、可整段复制）→ 〇 现状（活代码库增补必写，**引用状态前先现跑复核**）→ 必做清单（分小节编号）→ **输入 / 输出契约** → 固定约定 → **可勾选验收**（每条带判定方式与数字）→ 产出文件清单 → **禁止项** → 开放问题（**有阻塞性未知才反问**，否则在首步复述里点明理解，不许静默假设）。
- **每批四步**：① ≤20 行复述理解与拆法（唯一一次大改口径的机会）→ ② 输出验收清单 → ③ 分文件输出完整代码（单次 ≤600 行、文件边界明确）→ ④ 给可复制执行的自测命令。
- **硬要求**：「铁律措辞 + 禁止项 + 产出文件清单 + 可失败验收」四件缺一不可；**数字与口径不发明**——找不到出处的写进"开放问题"，不填感觉值；增量任务卡装配进已有批次，**不另建批次、不重做已验收模块**。

## 四、目标化执行（服从当前宿主与当前用户授权）

- 当前人类明确请求长期目标时，先写可失败验收，再按当前宿主 Goal 契约决定是否创建；文件数、旧任务包、历史未完成队列只是线索，不是新授权，也不自动要求建目标。已清楚且获授权的范围不重复询问。
- 状态转换、自动轮次、阻塞与恢复统一按 [long-task-discipline §7](../long-task-discipline/SKILL.md) 及当前宿主工具契约，不在此复制“两态收尾”或固定次数换路。自动续跑消耗配额，不承诺零成本。
- **目标 objective 必须含可失败判据**：例如对应真实验收命令、退出码、实际产物与计数；不发明不存在的验收命令。依赖用户裁决的口径先澄清，可查事实先查。
- 每个可交付单元：做 → 真实验证 → 在持久化授权内同步状态/下一格 → 核对剩余验收。只读或禁存任务只在回复总结，不创建或更新台账/经验/检查点；自动采集未核实前不宣称零写盘。
- 局部受阻时继续其余已授权可行项；全部受阻、取消、拒绝或恢复依宿主契约处理，不为凑次数换通道、不自动复活任务。
- **禁止**：把“跑了命令”“看起来对”“受阻”当完成；不静默缩小验收。正式计划、团队与危险操作批准继续保留。

## 分段检验与并行协作

- 每个可交付段先确定可失败判据，再实施、运行受影响验证并记录准确结果。失败保留首红；修复后先定向绿，再跑必要集成门。相关检查已通过且无新变更时继续下一段，不为凑次数重复全量构建。
- 累计验收还要覆盖跨段接口、最终冻结包与实际安装；每段通过不自动等于完整交付。测试、fixture、实际 SDK、现役实例和真实服务证据分层，未跑/跳过不算通过。
- 提示词优化复用[意图澄清](../intent-clarification/SKILL.md)，模型按当前目标重组目标/约束/验收，保留原意与已有授权，不在每条清楚请求前强加润色确认。
- 有独立工作且收益合理时，按需读[并行边界](references/parallel-execution.md)。不为提高并发而让多个写者争用同一源码、产物或前台。
- 文档格式沿项目现有约定；没有约定可用[最小任务账本](templates/task-ledger.md)，不强制所有任务都使用六节或批次包。
