# 文档生成规则

来源：Qoder 侧 `rules/doc-authoring.md` + 记忆 `feedback-parallel-doc-writers`，2026-09-20 迁移为 DSH 技能。

## 一、交付三件套（**整批生成 / 大修文档体系时**动工前必须就位，缺一不开工）

> **单点修改不建三件套**：只改一两页 / 补一条事实，直接改并给**回读证据**（改哪行、读回什么）即可。

| # | 文件 | 只放什么 | 判据 |
|---|---|---|---|
| 1 | **事实源**（如 `_FACTS.md`） | 已核验事实 + 精确 `路径:行号` + 冲突裁决。**所有页面由它派生，禁止凭印象写** | 每页每条事实都能追到事实源的一行 |
| 2 | **写手简报**（如 `_AUTHORING.md`） | 格式契约、禁编造清单、凭据一律 `<redacted>`、自查命令 | 写手 prompt 只需指向它，不需口头交代格式 |
| 3 | **校验脚本**（放项目 `scripts/`，可复用） | 解析 YAML/JSON、校验引用路径存在、`#Lx-Ly` 行号越界、内链可达、代码块/mermaid 闭合、疑似明文凭据、plan↔磁盘结构一致、索引页是否提到每一页 | **每完成一批就跑一次，不靠通读**；退出码 0 |

> 验证入口从目标项目当前清单和 AGENTS.md 发现；本包不附带项目专属的 check-wiki-refs.js。没有现成脚本时按本次影响选择检查方式，不伪造“本仓已有”。

## 二、结构约束（Qoder repowiki 形态；本仓沿用）

- 四层：`wiki_plan.yaml` + `knowledge/zh/_index.yaml` +
  `knowledge/zh/<模块>/{_module.yaml,概述,技术栈,架构设计,编码规范,特殊配置与命令}.md` +
  `zh/content/<章节>/<页>.md`。
- **`wiki_plan.yaml` 的 `documents` 是白名单＝上限**（≤50 页 / 顶级 ≤12 / 每顶级 ≤8 子页 / 仅 1 层嵌套，**超出静默截断**）。
  要更多页或两级子目录：**删掉 `documents`**，把结构写成 notes 章节地图，并让校验脚本切到
  "章节名单 + 索引页存在 + 每页被本目录索引提及"模式。
- `scope.include/exclude` 当前**不解析**，不要写；**YAML 双引号标量内禁用 ASCII 双引号**（用「」），改完立刻重跑解析。

## 三、多写手并行编排（本技能的核心）

### 3.1 关键实测数据（决定了下限怎么定）

同一批任务的对照：**"先通读代码再动笔"**的写手用 153/158/170 次工具调用、40M–53M subagent token
才写出第一页，正好撞轮次上限（150）而崩；改用**"禁止通读、事实只从事实源取、读完格式契约立刻写、
全程最多 3 次 grep"**的同类任务只用 **24 次工具调用、2.2M token** 就交付且校验 0 问题。

崩溃点集中在 **120–165 次工具调用 / 25M–47M token / 约 50 分钟**；
报错只有两种：`Reached the maximum turn limit (150)` 与平台通用的 `Sorry, something went wrong`。
**关键：崩前通常已经落了大部分文件。**

### 3.2 编排规则（每条都能判）

| # | 规则 | 判据 |
|---|---|---|
| 1 | 每个写手 **≤10 个文件** | prompt 里写死文件清单；`max_turns` 不如缩小 scope 可靠 |
| 2 | **领地严格不重叠** | 每个写手一个独占目录；共享索引页 / 跨目录登记**由主会话写**，写手禁改 |
| 3 | prompt 明写"**边写边落盘**，每写完一个立即写下一个，**不要先做大范围通读**" | 写手日志里第一个 `write` 出现在前 ~20 次调用内 |
| 4 | **取证预算显式设上限**（"最多 N 次 grep"），并写"**先写后查**" | 超出预算就回来问，而不是继续扫 |
| 5 | 开工前先给三件共享物（事实源 / 简报 / **金标准样页**），写手**只读不写** | 写手输出格式与样页一致 |
| 6 | **研究型任务不由写手做**：找事实交主会话或只读探索代理，**事先落盘成事实源**，写手只做转写与定点核验 | 写手不产生新事实，只消费事实源 |

### 3.3 中断恢复：先做差集，禁止整批重跑

写手异常退出后：

1. 列**已落盘文件**；
2. 只补缺口；
3. 把**已完成文件名写进重投 prompt**（防止它重复创建或改名）；
4. **禁止整批重跑**——会覆盖已完成页并引入新幻觉。

**半成品状态**下允许的唯一噪声是"指向尚未生成页面的内链不可达"，其余问题必须为 0。

## 四、事实冲突：复验与传播

- **写手回报的分歧一律当线索，不当结论**。复验按影响面分档：**高影响**（会改结论 / 要多处传播 / 涉口径）由主会话亲自复验再定性——
  `javap -c` 看分支常量、`grep -rlo` 数引用、`wc -l` / `svn status` 取计数；**局部可反证**的（单点计数、单条路径）采信写手给出的复验读数，抽查一条即可。
  **"类存在"≠"被调用"，"注解为零"≠"机制不存在"。**
  （实测被推翻的 6 条：连接池说成 Druid 实为 c3p0 缺省、以为无声明式事务实为全局 `HiatmpTx`、
  25 条路由实为 26 次 `me.add`、`COL_*` 95 列实为 91、`mail.*` 以为没用实为审核邮件在用、
  空 catch "24 处 TODO" 按两种口径分别是 12 / 24。）
- **结论定了要四处传播**：事实源 → plan notes → 知识卡 → 各页面。手工改会漏，
  写**一次性 codemod** 按精确字符串替换并**打印命中数**；
  **必须排除事实源与待办文件**，否则会咬掉"早期文档写'25 条路由'是漏了…"这类引用句；
  改完 `grep` 复查含"旧说法 / 早期文档 / 以本页为准"的句子。
- **口径冲突写成双口径并列**，不互相否定；无证据的写"未确认 + 缺什么证据"。

## 五、批量改文档的两个自伤点（都实测过）

1. **把 ASCII 双引号写进 YAML 双引号标量** ⇒ 整个 `wiki_plan.yaml` 解析崩
   （`bad indentation of a sequence entry`），依赖它的脚本一起崩。中文语境极易写出
   `不得"修正"为…`，改用「」；改完**立刻重跑解析**。
2. **无差别字符串替换会咬到"引用旧结论"的句子**（见 §四的排除规则）。
   校验脚本要把这两类做成常驻检查：YAML `try/catch` 解析（失败即报问题而不是崩栈）+
   扫"双引号标量内的裸 ASCII 引号"。

## 六、收尾

- **重写整套文档前先快照**（`.qoder/repowiki.bak-<date>`）；快照里的明文口令**顺手脱敏**。
- 清理一次性脚本与中间文件。
- 汇报严格区分"已落地并验证"与"未做 / 未验证"；文档类任务的判据是
  **"校验脚本全绿 + 抽查读码"**，未真实运行程序要明说。

## 八、wiki 三条铁律（有 wiki 的仓）

> **有 wiki 的仓才适用这三条**；无 wiki 时按 §一 处理（按影响面决定要不要建），**不要为凑这三条去建 wiki**。

1. **有 wiki 先查 wiki 再动手**——先定位模块 / 入口 / 约定，别一上来通读源码。
2. **代码产生改动后同批回写**受影响的页（含 `<cite>` 与 `file://#Lx-Ly` 行号）。
3. **wiki 与代码冲突以代码为准**，就地修正并在汇报里点出冲突。校验读数别自己猜：`#L1-Ln` 整文件锚点越界只作计数说明，`lo>1` 的切片越界与 `#L31-L...` 这种残缺才报——判据写宽会一次刷出上百条噪声，噪声多就会被忽略。

## 九、方案文档运行时复核（评审 / 验收方案文档时）

- **任何基于代码 / 数据库的方案文档，评审前必须真机实测复核**——不能凭"合理假设"编写，不能用"印象"代替事实；文档里每条事实断言都要能指到**实测证据**。
- 逐条实测：**文件 / 表 / 字段 / 接口 / 端口 / 行号**是否真实存在，口径是否与现网一致；「**快照**」与「**现网实测**」必须**区分**（快照会漂移）。
- 拿不到实测证据的结论显式标注「**未验证 + 原因**」，不写成确定事实。
