# 把纪律做成会判红的门禁

## 何时用

一条纪律被反复违反、或"文档里有但现场没拦住"时。改文案几乎从不解决问题——缺的是**能失败**的判据。

## 五步

1. **缺口取证**：给出真实反例（哪一次、哪条命令、哪份日志），而不是"感觉经常犯"。没有反例就先观察，别先写守卫。
2. **选承载**：按覆盖面从大到小选——原生守卫（宿主层，覆盖所有预设）> hook（只覆盖挂了它的那层）> 周检脚本（覆盖静态声明）> 文档。选错层的典型症状：挂了 hook 却发现跑在别的预设上不生效。
3. **判据单一真源**：可执行判据只写一处（守卫脚本或周检脚本），文档只写"为什么"和"去哪看"。两侧各写一份判据 → 必然漂移。
4. **两侧分工**：前置只做**拦截**（拦得住就够，别顺手改文件）；事后只做**记账与体检**。前置里做修复，会在失败路径上制造二次副作用。
5. **三层自测**：
   - 正例：合法操作必须放行（放行不掉说明守卫写死了）；
   - 负例：违规操作必须被拒（拒绝不掉说明判据没生效）；
   - 变异：把判据改一个字符，必须从绿变红（恒真的判据等于没有判据）。

## 收口判据

- 门禁脚本 `-Check` 退出 0 且报告里 `ok=true`；
- 负对照（临时指向不存在的输入/删掉一条判据）退出 1；
- 台账非空核查：门禁必须证明"它检查过东西"（比如扫描到的条目数 > 0），不能空跑即通过；
- 周检与提及扫描复跑一次。

## 反例

- 只跑正例就宣布"门禁生效"——最常见假绿；
- 守卫放在扫描之后，扫描失败时守卫根本没轮到执行；
- 前置脚本顺手格式化/修复，失败路径上留下半成品；
- 编码不一致（子进程 UTF-8、宿主按本地代码页解码）导致判据把正常输入读成损坏 → 门禁恒红，红久了没人再看它。
