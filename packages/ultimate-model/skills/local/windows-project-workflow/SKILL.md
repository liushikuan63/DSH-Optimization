# Windows 项目工作流

本机的项目集合是 `<盘符>:\Java\GitHub`，并不限于 Codex 当前 cwd 或注册工作区。先确认用户指定的项目/模块和当前配置，再选择验证入口。目录归属和版本请在目标机现查（本机工作区清单属机器数据，不随技能包分发）。项目说明里的旧状态是线索，当前源码、配置与实际结果是事实依据。

## 预检与定位

- 先读适用的全局、父目录和最近的项目 `AGENTS.md`，检查目标子仓的 Git 状态；不同会话的修改应保留。在多仓父目录中工作时先定位子仓。无 Git 的源码导出仍是用户项目，不为预检擅自初始化仓库。
- `.git` 文件、Git common dir 与 `git worktree list` 决定 worktree 关系；带日期、`sbx`、`stage` 等名称本身不能证明目录可弃用。`tieshi` 有明确迁移标记，应先核验真源；已有 dirty worktree、发布副本、数据和历史产物保持其既有角色。
- 需要快速识别环境时，运行本技能的 `scripts/preflight.ps1`：
  ```powershell
  pwsh -NoProfile -File '<本技能目录>\scripts\preflight.ps1' -ProjectPath '<目标仓库>' -IncludeToolVersions -AsJson
  ```
  脚本只读清单、锁文件、规则位置、Git 状态和版本信息，最多搜索三层，跳过依赖/构建/历史目录；它不安装依赖、启动服务或证明项目可运行。它输出的是清单摘要，版本继承与命令效果仍须读实际 POM、CI 和项目脚本。
- 按 Maven/Gradle wrapper、POM、`package.json` 与锁文件、Python 清单/环境、Cargo 清单选择工具链和包管理器。`java -version` 与 `mvn -version` 可能指向不同 JDK；本机项目声明的目标 Java 8/11/17/18/21 并存，按当前模块配置工作。多个 JS 锁文件并存时先核对 CI/最近维护入口，不按文件名顺序猜包管理器。
- 优先项目已有环境脚本，只改变当前任务/子进程环境。在需要 Git Bash 的仓库中明确调用 Git 安装中的 `bin\bash.exe`，核验后再用；不要把 PATH 中的 WSL bash 当作等价入口。
- 遇到 Git Bash 调 Windows 程序、PowerShell 版本混用，或参数/编码/退出码异常时，读取 [跨 Shell 诊断](references/windows-shell-boundaries.md)，按实际解释器、argv、原始字节和进程退出码做对照。
- 按当前技术栈在目标机现查对应的工作流提示；不要将一个仓库的版本或产品规则套给其他项目。整机盘点类清单属机器数据，不随技能包分发。

## 当前步骤的工具工作集

先确定当前步骤需要的能力，再在实际可用工具的名称/描述中定向检索；读取候选的必要 schema、技能段落和文件片段，取到足够证据后行动。能力不足再扩检，不反复输出全工具目录或完整日志。保留少量相关入口和证据指针；离开该领域时不继续携带整份材料。缓存路径和旧工具名只是线索，再用时复验可用性；此做法不要求修改宿主的工具注册或权限。

## 实现与相关验证

- 沿用户操作、客户端调用、接口、服务及存储定位实际生产路径；修改契约/生成源时复用生成器，不手改生成物。
- 查第三方 API/版本兼容问题时使用已连接的 Context7 或官方文档，只发送公开库名、版本与必要问题。
- Maven 测试需核验 `maven.test.skip` / `skipTests` / Surefire 当前有效配置，并检查实际报告、失败/跳过/执行数量；零测试或仅编译不能算测试成功。前端脚本取自当前 `package.json`，Rust 复用仓库的 MSVC/Cargo 入口。
- Vue 2/Vue CLI 与 Vue 3/Vite 按现有实现区分，不将 `<script setup>`、Pinia 或框架大版本迁移变成日常修改。pnpm monorepo 从根 workspace 与 filters 选择包；Cocos、Electron/JCEF/Tauri、Capacitor 的产物/桥接验证各有不同，网页验证不能替代原生端验收。
- Android 优先当前 Gradle wrapper 与 SDK/AGP/Kotlin 配置；交互/性能任务使用已安装 Android QA/性能技能。缺 adb 时先定位已有 SDK，不借预检安装或运行不明设备操作。Python 使用项目解释器/虚拟环境/uv/pip 声明，缺清单的源码树只记录缺口，禁止执行 setup.py 或云部署脚本来猜依赖。
- 对交互或跨端改动验证真实流程，并确认运行进程、页面、端口及产物属于目标 checkout。构建会清空产物目录时，先等构建完成再运行 UI 探针。独立读取或不共享产物的检查可以并行。
- 选择与改动匹配的检查；项目要求更完整的验收时遵循项目规则。纯文案、配置摘要等低风险修改不机械运行全套重型测试。
- 仓库已有任务卡/台账时按其约定记录本轮事实、证据和剩余项，避免另建重复记录；提交、推送和发布仍以当前会话授权为准。
- 用户要求接续长期批次时，沿现有任务队列选下一项，保留已完成、验证、关键决策、下一项和阻塞入口；压缩后恢复这些指针并继续已授权任务。Qoder/dsh 规则与历史记录只用于理解既有工作方式，不继承其他平台的超时自动批准、自动推送或 Stop hook 行为。

## 失败分类与有界恢复

- 先区分临时传输问题、确定性输入/契约错误、凭据/配额、环境前置与用户取消；按完整错误和实际条件判断，不只按 AUTH 等前缀归类。确定性错误先修因；凭据、配额和取消不靠重复调用解决。
- 在原任务记录里限定次数或时间预算，并保留已耗预算及每次新证据；同一失败无条件变化时停止重复策略并换诊断。任务卡、工具或宿主已有重试时避免再叠一层；持久预算不因新轮次、空闲或一般用户消息自动重置。
- 重试前判断操作是否幂等、是否可能已生效。读超时可在预算内重试；提交或发布超时先按操作标识只读查回，再补缺失步骤，不能把超时当失败而重复写入。取消或目标变化撤销旧的待执行方案。

交付时说明改动、实际执行的验证与结果、未完成的验证及原因，检查最终差异和改动归属。
